# Fixed-source vocabulary retest: remove the two-file rule

**Status:** proposed, not a frozen run. No new results. The [v1 freeze](fixed-source-v1/FREEZE.md) and [v1 results](fixed-source-v1/RESULTS.md) remain unchanged and apply to their own rules.

**Question:** On the same fixed source bytes and budgets, what changes when a multibyte entry may come from only one file? The primary result is the unrestricted experiment, not a reinterpretation of v1. This is in-sample representation, not transfer, model performance, semantic reuse, or a compression claim without end-to-end storage accounting.

## Inputs and matched policies

- Reuse the exact [v1 manifest](fixed-source-v1/manifest.json): the same 400 problems, one Python and one JavaScript file per problem, 800 byte-identical files total. Verify each SHA-256 before mining and replay. No rewriting, renaming, helpers or raw escapes; no held-out or protected files. Strings are byte substrings; a candidate cannot cross a file boundary.
- **Primary: support ≥1, whole files allowed.** Every nonempty observed source substring up to maximum length L is eligible subject to the mode. A whole file is allowed only if it meets the same L, entry-count and serialized-byte budgets as any other string; there is no side channel or exemption.
- **Historical matched control: support ≥2, no multibyte whole-file entries.** Count distinct files, not occurrences; if a multibyte entry equals any whole file in the relevant corpus, exclude it even if it is present in another file. Singleton mode rules are the same as in the primary arm.
- **Isolation control: support ≥1, no multibyte whole-file entries.** Add this intermediate wherever allowing whole-file entries changes the candidate set in the relevant corpus, L and mode. It isolates the support effect from the whole-file rule. Before search, record minimum file length, counts of eligible whole-file strings, and the candidate-set comparison by corpus, L and mode for these two policies. Collapse an identical intermediate cell with evidence, not by assuming it is identical at L=16. Character-only results are one invariant control, not duplicate evidence.
- Support is measured within the candidate dictionary's source pool: all 800 files for shared; the relevant 400-file language pool for each separate dictionary. Verify and report the three corpus views independently. A raw v1 row is historical context rather than a matched control; v1's special BPE-free arm is not a substitute for this retest.

## Modes, budgets and metrics

- Run **mixed** (one-byte and multibyte entries allowed), **characters only** (one-byte entries only), and **no-singleton** (entry lengths 2 through L). A coverage search must not require the complete alphabet to be allocated before it starts; if a full-coverage greedy or baseline algorithm seeds it, label that implementation choice. At L=1 no-singleton is structurally empty.
- Use v1's grid: K = 64, 96, 128, 192, 256, 384, 512, 768, 1024, 2048, 4096; L = 1, 2, 4, 8, 16, 32, 64; B = 1, 2, 4, 8, 16, 32, 64 KiB or uncapped. Caps are maxima, not targets. Freeze a single reference dictionary serialization before running: the v1 accounting convention is one length byte plus payload per entry and four routing bytes for separate dictionaries. Count actual bytes from the frozen representation, including any framing, verify every tested prefix and charge all framing or routing consistently; do not mistake private JSON or debug-chain size for the claimed representation. Record actual length and count even for uncapped cells. Apply exactly the same combined K/B caps and split grid to shared and separate.
- Use the same predeclared search/baseline implementations, objective, shortest-path parser, deterministic tie rules and work limits across eligibility policies. Apply the policy to every retained dictionary entry, including BPE merges and local refinement. Report ordinary BPE separately on the same codebook. Match search/refinement effort or explicitly distinguish a matched baseline from extra search. Record stopped/incomplete cells, never turn a cap hit into a negative result.
- Report files reconstructed, total shortest-path tokens only for complete coverage, tokens on covered files separately with the denominator, actual serialized bytes, support-1 and whole-file entry counts and usage, time and peak memory. For no-singleton, separately report verified single-dictionary budgeted coverage, individual unbudgeted reachability under the selected policy, and the unclassified difference. Do not reuse the v1 forced-cut or rank conclusions for the primary arm. Report a new bound or proved optimum only after its policy-matched certificate passes the independent checker.

Under the unrestricted policy with K/B ignored, positive-length files in no-singleton mode are reachable exactly when even at L=2, and all lengths ≥2 are reachable at L≥3 (write the length as a sum of 2s and 3s). A one-byte file is never reachable without singletons. Mixed mode at L≥1 reaches every file before imposing K/B; empty files, if present, need no entries. Check these identities against the independent graph. They do not imply that one fixed-budget dictionary covers those files.

## Required verifier and regression changes

Implement the runner/checkers in a versioned sibling, leaving all of fixed-source-v1 untouched. Each receipt must bind policy (including whole-file handling), pool, mode, manifest digest, implementation, K/L/B, work limits and run identity. Reject missing or conflicting fields; do not infer policy from a filename or trust the searcher's flags.

1. Update candidate enumeration and all consumers (equivalents of v1's engine.c, bound.c, run.sh and pipeline.sh) to propagate explicit eligibility and mode, including prefix-growth pruning, BPE and polish. For support ≥1, length growth must retain starts for legal longer candidates, even when a current prefix would not itself be an eligible entry.
2. Update the independent dictionary/replay and shared/split checkers (v1 equivalents verify.py and verify_sharing.py). Independently count distinct-file support and enforce whole-file rules, membership, nonempty and byte lengths, mode, duplicate prohibition and exact budget; check framing at every scored prefix. Parse each claimed file, reconstruct byte for byte against its manifest hash, and recompute per-file coverage and score. Recheck both shared and separate artifacts and each feasible selected split under its declared policy.
3. Update independent limits/certificate checkers and report generators (v1 equivalents check_limits.py, check_bound.py, analyze.py and make_figures.py). Reconstruct each selected policy's exact candidate graph, including any newly legal whole-file entries, and independently check reachability and applicable integer bounds. Never reuse a v1 certificate as v2 evidence without a fresh exact policy verification. Make omissions, infeasible cells, timeouts and uncovered-but-reachable files distinguishable.
4. Before corpus search, use tiny brute-force fixtures: a substring repeated within just one file; a multibyte entry that is both a whole file and a substring of another; cases below and at L/K/B and with routing overhead; a singleton-mode violation; an entry absent from the pool; a wrong manifest or policy binding; and corruption of one intermediate prefix length. Verify a clean case for each mode; at least one fixture must fail the historical control and pass the primary with the same verified bytes. Exercise the all-eligible reachability vs single-budget witness distinction.

## Freeze and run

Commit a new immutable fixed-source-v2/FREEZE.md before new dictionary mining, with the resolved policies, manifest digest, grid and primary endpoints (pooled K=256/L=16 complete-coverage emissions and K=4096/L=16 no-singleton coverage; include uncapped and preregistered byte-capped views), baseline versions, validator gates, analysis and stop rules. Any subsequent change gets a new freeze and run ID. Keep source, private dictionary bytes, parses and certificates outside Git; publish only agreed redacted aggregate tables, code, hashes, and evidence status.

This pipeline is CPU-only. Start with synthetic fixtures, then a bounded, explicitly logged CPU pilot after freeze to measure candidate enumeration, search and verifier wall time and peak RSS. Freeze the pilot scope and decision rule for full-grid sizing in advance; do not use its outcomes to retune scientific endpoints. Pin worker count, imposed process wall/CPU/memory limits, separate enumeration/search/replay times and kill behavior, before the full matrix. v1's 8 workers, 45-minute chain setting and 32 GB are historical ceilings, not a measured v2 completion time. Do not open a GPU run for this retest.
