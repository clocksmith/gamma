# Systematic incremental family vocabulary growth

The owner-directed method is gradual vocabulary expansion and merging, not a
parameter sweep. Freeze all300 development-fit problem IDs and the independently
qualified same-language source alternatives from the preceding400 source pool.
The100 development-validation and final100 sources do not generate proposals.
All500 M1 gates remain unchanged; this is fit evidence, not qualification of M1.

Assign each problem one fixed pre-cost source-structural organizational label:
node-children, node-next, nested-index, keyed-collection, sequence, scalar-other,
using the exact ordered classifier in run.py on the frozen reference. These are
syntactic families, not claims about semantic domain or correctness authority.
All variants of one problem remain in its family and count as one support owner.

Start each local family at the96-character alphabet. Slowly add up to32 learned
literal entries. At each step derive every adjacent-pair concatenation from the
exact canonical segmentations of EVERY qualified variant, requiring support in
at least2 distinct problems. No64-character cap or top-k proposal truncation.
Exclude whole-source/body literals and any wrapper containing such a body.
Conservatively exclude every complete named helper definition/body too, pending
an explicit generic-primitive audit; a shared helper can still be a whole solver.
Exhaust the deterministic proposal worklist with exact resegmentation and joint
source reselection. Choose the lexicographically best resulting gate vector:
counts above96, counts above32, max(0,10C-S), totalS, totalC, literal bytes.
This fixed ordering is a heuristic preference, not proof of global optimality.
Per-problem source reselection minimizes selections then character selections;
it is not an exact global optimizer of the gate-vector source-choice problem.

Merge the pair of family vocabularies with the most shared literal UTF8 bytes,
then most shared entries, then lexical identifiers. Deduplicate identical exact
strings. Shared entries seed the merged language; the union is a PROPOSAL POOL,
never an over-capacity decoding language. Allocate remaining union pieces by
exact marginal cost, remove entries only after exact per-problem nonregression
and nonincreasing character cost, then expand with fresh adjacent compositions.
Repeat until all families share ONE language. Run the same procedure separately
at128/seven-bit and256/eight-bit capacities. No hidden family selector or dispatch.

Each accepted addition/removal/merge records a hash-linked ledger, exact source
choices, per-step marginal coverage/cost and a nondominated frontier for its
problem subset. Independent segmenters and packet decoder validate every ledger
state; source, dictionary framing, packets and decoder bytes are fully charged.
The ledger and strings stay private. A CPU slice pauses, never claims completion;
resume only with identical code/source/contract hashes. Finished growth phases
reuse hash-checked accepted entries; an interrupted candidate scan restarts from
the last accepted state. All candidate evaluations remain source-as-data only.

Initial supply is fixed to the566 previously qualified source variants (fit-only
subset admitted here). Further qualified structural/direct-entry alternatives
require a successor supply freeze, linked to this complete or paused ledger;
never mutate the current source pool. Report losses as well as gains, and do not
interpret a restricted adjacent-composition stall as impossibility of M1.
