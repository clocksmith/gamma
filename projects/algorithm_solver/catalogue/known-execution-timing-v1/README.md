# Known-ID verified execution timing

This completed bounded diagnostic measures the optional known-ID **input execution**
mode: receipt-bound source retrieval, live protection/hash checks, public-domain
input admission, fresh isolated JavaScript/Python execution, independent typed
result/mutation/alias verification, and response serialization. Three frozen
public probes (802,875,2406), five repeats per language,30 calls.

Service initialization is measured separately. Each candidate process is fresh;
OS cache state is uncontrolled, not a cold-cache assertion. Raw observations and
process status are retained privately after the response-timing interval, and
`verify.py` independently replays all30 outcomes and response hashes. Failures
remain failures. Timing arithmetic is checked, not independently clock-attested.
Parent peak RSS and largest individual child peak are separate, not an invented
simultaneous process-tree peak.

The exact operator freeze binds sources indirectly through the reviewed public
qualification contract, service/catalogue, runtime and all code identities.
Expected results stay outside candidate isolation. No private corpus loader or
protected source/case is consulted. Candidate limits stay3CPU/8wall/1GiB/4MiB;
outer120CPU is a parent per-process cap, not an aggregate child CPU cap;
180wall/2GiB. Tests use synthetic injected adapters only.

This does not measure informal description encoding/recognition, network
transport, or execution across the whole4081 catalogue. It is a concrete1c
mechanism/diagnostic, not completion of1c or proof of general correctness.
Initial unrun proposals were superseded to preserve raw evidence and accurately
label memory; their artifacts remain unchanged.
