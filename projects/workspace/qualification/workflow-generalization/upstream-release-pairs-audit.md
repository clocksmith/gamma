# Upstream Open-Source Release Pairs: Atomic Predicate, Optimistic-Lock, and Idempotency Selection Audit

Prepared before live Stage 2 execution (`#88`). Regardless of whether `gammatron-graph` or `attested-checkpointed-skill` runs on the client, Theorem 2's write-safety guarantee depends on whether the target application's **existing server API/database transaction** can enforce optimistic version locks and cross-entity prerequisites **atomically at mutation**.

Below we audit six self-hosted open-source web applications across tagged `Release N -> Release N+1` pairs, separating **Tier A (Selected Stage 2 Candidates whose stock APIs enforce optimistic locks + transactional cross-entity predicates natively)** from **Tier B (Single-entity or last-write-wins stock APIs that require either partial-contract race flags or a ~62--100 LOC transactional gateway)**.

---

## 1. Tier A — Selected Upstream Release Pairs With Native Transactional Predicate Enforcement

| Application & Release Pair | Documented `N -> N+1` UI / Workflow Drift | Target-Record Optimistic Lock | Atomic Cross-Entity Predicate Check at Mutation | Lost-Ack Retry Idempotency | Direct Write-API vs. Browser UI |
| --- | --- | --- | --- | --- | --- |
| **OpenProject** (`v13.4.0 -> v14.0.0`, Rails + PostgreSQL) | GitHub Primer page-header overhaul, work-package hierarchy progress rollup redesign, and `delay -> lag` relation terminology shift | **Mandatory `lockVersion: <int>`** on `PATCH /api/v3/work_packages/{id}` (`409 Conflict` `UpdateConflict`) | **Native transactional DB contract:** `WorkPackages::UpdateService` + `UpdateContract` validates workflow status transitions (`workflows`), member roles (`member_roles`), and parent/type constraints **inside one PostgreSQL `ActiveRecord` transaction** (`422`/`403` on revoked role/workflow rule) | **Natural on `PATCH` updates:** committed update increments `lockVersion` ($v \to v+1$), so retrying with `lockVersion: v` fails closed (`409`) and reconciles via `GET`; `POST` creation still needs a ~26-LOC sidecar journal | Direct REST API (`PATCH /api/v3/work_packages/{id}`, `POST .../custom_actions/{id}/execute`) covers CRUD; multi-screen UI staging applies to Primer split-screen / meeting-linked work-package configuration |
| **Frappe Framework / ERPNext** (`v15.10.0 -> v15.20.0`, Python + MariaDB/PostgreSQL) | Desk multi-tab form layout, child-table grid controls, and workflow action state-bar updates across `v15` minor releases | **Default `doc.modified` microsecond lock** on `POST /api/method/frappe.desk.form.save.savedocs` & `apply_workflow` (`frappe.TimestampMismatchError` unless `ignore_version=True`) | **Native single-transaction validation:** `apply_workflow` checks `Workflow` transition rules/roles and `doc.validate()` queries linked prerequisite DocTypes (e.g., `Quality Inspection`, `Budget`, `Supplier Quotation`) **inside the same uncommitted SQL transaction** before `frappe.db.commit()` (`ROLLBACK` on revoked prerequisite) | **Natural on versioned `savedocs` / `apply_workflow`:** committed save bumps `modified`, so any retry carrying the pre-commit `modified` timestamp aborts with `TimestampMismatchError` (`0` duplicate transitions); `insert` requires unique naming or sidecar journal | Direct RPC covers scripted saves; Desk UI covers multi-screen wizard/child-table staging before `Submit` (`docstatus: 0 -> 1`) |
| **Gitea** (`v1.21.11 -> v1.22.0`, Go + SQLite — *endpoint-split boundary*) | Repository PR review/header template refactor across `1.21 -> 1.22` | **Split:** `head_commit_id` enforced on `POST .../pulls/{index}/merge` (`409`/`405`), **absent** on `POST .../pulls/{index}/reviews` and `PATCH .../issues/{index}` | **Atomic on `merge` only:** `Merge()` verifies `head_commit_id`, branch-protection rules, and required approval counts at commit; **non-atomic on review/issue staging** | **`merge` is state-idempotent** (`merged: true -> 405`, `0` duplicates); **`POST .../reviews` duplicates** on retry without a sidecar journal | Direct REST API covers PR reviews & merges; non-merge UI review staging must report `unconditionalWriteRaceWindow: true` unless wrapped |

**Critical Tier A boundary (`DB-truth` vs. caller-pinned `predicateVersions`):** OpenProject (`UpdateContract`) and Frappe (`doc.validate()`) check **live transactional database truth** of separate role, workflow, and linked-document tables at commit time (`0` writes if an approval/role is currently revoked), whereas they do not verify a caller-supplied historical `approval_version` integer if an approval was revoked and re-granted under different terms without violating `UpdateContract`/`validate()`. Workflows requiring exact caller-pinned sibling versions (`predicateVersions`) need either a custom validator rule (~15--25 LOC) or a transactional proxy (~36 LOC).

## 2. Tier B — Candidate Release Pairs Lacking Cross-Entity Atomic Preconditions Out of the Box

| Application & Release Pair | Single-Record `If-Match` / `ETag` | Atomic Cross-Entity Preconditions | Native `Idempotency-Key` | Stage 2 Disposition |
| --- | --- | --- | --- | --- |
| **Vikunja** (`v0.23.0 -> v0.24.0` / API v2, Go + SQLite) | **Yes** (`If-Match` / `ETag` -> `412 Precondition Failed` on `/api/v1/tasks/{id}`) | **No (`singleEntityWriteRaceWindow: true`):** project/team permission changes on `/projects/{id}` do not bump `/tasks/{id}`'s `ETag` | **No** on `POST` task creation | Eligible **only** as single-entity `ETag` partial-contract control or behind a SQLite/HTTP gateway |
| **NetBox** (`v4.4.0 -> v4.5.0`, Django + PostgreSQL) | **Yes in `v4.5+`** (`ETag` on object REST endpoints) | **Not stock** (requires a `CustomValidator` plugin registered in `CUSTOM_VALIDATORS`, which runs inside Django's `@transaction.atomic` request wrapper) | **No** (relies on model unique constraints -> `400`) | Eligible if paired with a ~20-LOC `CustomValidator` enforcing linked change-control state |
| **Kanboard** (`v1.2.37 -> v1.2.40`, PHP + SQLite) & **BookStack** (`v24.02 -> v24.05`, Laravel + MySQL) | **No** (`unconditionalWriteRaceWindow: true`, stateless last-write-wins) | **No** | **No** | **Disqualified from unmodified Theorem 2 claims;** usable only under explicit `unconditionalWriteRaceWindow` disclosure or a ~62--100 LOC transactional sidecar |

## 3. Recommended Stage 2 Selection & Pre-Execution Approval Gate

To test live `Release N -> Release N+1` workflow generalization **without** confounding client representation results with broken server concurrency:
1. **Primary atomic-capable pair #1:** **OpenProject `v13.4.0 -> v14.0.0`** (Primer UI overhaul + hierarchy progress changes; native `lockVersion` `409` + PostgreSQL transactional `UpdateContract` across `work_packages`, `workflows`, and `member_roles`).
2. **Primary atomic-capable pair #2:** **Frappe / ERPNext `v15.10.0 -> v15.20.0`** (Desk multi-screen draft staging (`docstatus = 0`, stopping before irreversible `Submit` `docstatus = 1`); native microsecond `modified` `TimestampMismatchError` + single-transaction `Workflow` & linked-DocType `validate()`).
3. **Lightweight SQLite contrast pair #3:** **Vikunja `v0.23.0 -> v0.24.0`** or **Gitea `v1.21.11 -> v1.22.0`**, explicitly testing partial-contract (`singleEntityWriteRaceWindow` / endpoint-split) behavior alongside each app's Direct REST API.

**Hard Stage 2 gate (`$0` spent to date):** Do **not** launch paid live-planner runs in [`release-drift-runner.mjs`](./release-drift-runner.mjs) (`--approve-paid-model`) until the owner approves (a) the exact workflows and local container tags, (b) isolated local test accounts per run, and (c) the paid spend cap (`$40` total / `$2` per run remain proposals).
