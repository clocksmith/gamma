# N1: ERPNext v15.53.0 to v15.54.0, Sales Invoice stops fetching timesheets

One command runs the whole case (three repeats, each on a freshly brought-up pair of sites, then the result
file):

```text
SCREEN_OUT_DIR=<scratch directory> SCREEN_HOLD_FILE=<hold marker file> ./run.sh
```

| File | What it does |
| --- | --- |
| `run.sh` | Per repeat: waits while the hold marker exists, runs the frozen `../../../bringup/erpnext-up.sh v15.53.0 v15.54.0`, runs `run_case.py`, runs the frozen `erpnext-down.sh`, removes the anonymous volumes its own containers had mounted. A repeat that overlapped a hold is set aside as void and run again on a fresh pair. Ends with `assemble.py`. |
| `run_case.py` | Set-up, gates A, B and C, and the database reads, for one repeat. Writes `repeat-<n>.json` to `SCREEN_OUT_DIR`. |
| `assemble.py` | Applies the disposition table of `../../README.md` to the three repeats and writes `../../results/N1.json`. |
| `case_meta.py` | The case's conditions, deviations and notes, as recorded by the runner's operator. |
| `screenlib.py` | Request, command and hold helpers (Python standard library only). |

## Set-up

All set-up goes through the application's REST API in a session of `Administrator` (the site's own
administrator; its password is generated by the bring-up and never written here):

- the seeded account `stage2_author@isolated.local` (already an Accounts User) also gets the role Projects User;
- service item `SVC-A` (non-stock, group Services, unit Hour) and activity type `Consulting-A` (billing rate 100);
- per gate: customer, project and one submitted timesheet with one billable row of 8 hours at 100 on the
  project. Gates A and B use `CUST-A` and `PROJ-A`; gate C, on the same v15.54.0 site, uses `CUST-C` and
  `PROJ-C`. A project's document name comes from a naming series, so each project is renamed with
  `frappe.client.rename_doc` to make the sealed request's `"project": "PROJ-A"` address it literally.

## What each gate sends, as `stage2_author@isolated.local` with its own API key

- Gate A, v15.53.0: `POST /api/resource/Sales Invoice` with
  `{"customer": "CUST-A", "company": "Stage2 Qual Corp", "project": "PROJ-A", "items": [{"item_code": "SVC-A", "qty": 8, "rate": 100}], "docstatus": 1}`.
- Gate B, v15.54.0: the identical request.
- Gate C, v15.54.0: `POST /api/method/run_doc_method` with the unsaved draft and `method: add_timesheet_data`
  (what the page's Fetch Timesheet button calls), then the same create-and-submit request with the
  `timesheets` rows that call returned.

Success is HTTP 200. The stored value is read from MariaDB in the database container: the `Sales Invoice`
rows of the customer, their `Sales Invoice Timesheet` rows, the `Timesheet` row and its `Timesheet Detail`
row. Right value, from the sealed list: one `Sales Invoice Timesheet` row for the invoice with the timesheet
and 8 billing hours, `total_billing_hours` 8 on the submitted invoice, the timesheet 100 % billed with status
`Billed`, and the timesheet detail row pointing at the invoice.

No secret is written to the evidence: credentials are recorded as `<redacted>`.
