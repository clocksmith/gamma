# enwiki9 Custom Compression Algorithms Reference

This document provides a detailed technical reference for the custom-built, non-standard compression algorithms developed in this repository. Unlike traditional context mixing tools (like Cmix/PAQ), these algorithms explore structural parsing, online neural training with zero-byte parameters, and hybrid match-prediction frameworks.

---

## 1. `typed_anchor_chain_ppmc_v1` (Hybrid LZ77 + PPM Context Coder)

### Concept & Core Architecture
This algorithm is a **hybrid context-directed compression engine** that combines sliding-window match dictionary coding (LZ77) and prediction-by-partial-matching (PPM-C) over hierarchical document state chains.

```
                    ┌────────────────────────┐
                    │  Wikitext Parser (GST) │
                    └───────────┬────────────┘
                                │ Context State / Anchor Keys
                                ▼
 ┌──────────────┐   ┌────────────────────────┐   ┌────────────────────────┐
 │ Raw LZ77     │   │ Anchor Chain Match     │   │ Literal Character Mode │
 │ Match Window │   │ (History matching same │   │ (Adaptive PPM Model)   │
 │ (Distance/L) │   │  structural keys)      │   └───────────┬────────────┘
 └──────┬───────┘   └───────────┬────────────┘               │
        │                       │                            │
        └───────────────────────┼────────────────────────────┘
                                ▼
                    ┌────────────────────────┐
                    │ Rate-Distortion Opt    │
                    │ (Gain threshold > 0.5) │
                    └───────────┬────────────┘
                                ▼
                    ┌────────────────────────┐
                    │ Arithmetic Coder (AC)  │
                    └────────────────────────┘
```

### Components

#### A. Global State Tracker (`GST`)
The parser tracks wikitext state variables dynamically at each character without storing the full AST:
*   `f` (Field flag): Tracks XML tag regions (e.g., `<title>`, `<id>`, `<timestamp>`, `<comment>`, `<text>`).
*   `w` (Wikitext braces): Identifies whether the cursor is inside links (`[[`), templates (`{{`), or tables (`{|`).
*   `slot` (Template/XML category): Categorizes structures like `Category:`, `Image:`, `Cite`, `Infobox`, `Url`, `Title`.
*   `col` (Column index): Horizontal cursor offset on the line.
*   `word` (Trailing alpha characters): Tracks active text token.

#### B. The Matching Methods
At each offset `i` in the stream, the compressor evaluates two types of matches:
1.  **Raw LZ77 Match (`rawm`)**: Standard dictionary match. Scans history for identical substrings of length $L \ge 4$.
2.  **Anchor Chain Match (`chainm`)**: Scans historical positions that shared the **exact same hierarchical anchor state context** (keys generated by `GST.keys()`). If those historical positions contain matching bytes, they are encoded as an index into that specific context list.

#### C. Rate-Distortion Optimization (RDO)
Rather than greedily outputting matches, the encoder models the precise bit-cost of all choices:
$$\text{Cost}_{\text{literal}} = \sum \log_2(\text{PPM}(b_i)) + \text{Cost}_{\text{literal\_event\_flag}}$$
$$\text{Cost}_{\text{match}} = \text{Cost}_{\text{match\_event\_flag}} + \text{Cost}_{\text{match\_offsets}}$$
*   **Decision:** The encoder computes $\text{Gain} = \text{Cost}_{\text{literal}} - \text{Cost}_{\text{match}}$. If $\text{Gain} > 0.5$ bits, it emits the match; otherwise, it encodes the literal via PPM.

## 2. `purple_parrot_nncp_v1` (Zero-Weight Online Neural LSTM)

### Concept & Core Architecture
This program uses a **1-layer character-level LSTM language model** to predict the next byte distribution. Its defining feature is that it ships with **zero pretrained weights**, resolving the primary Hutter Prize penalty where model parameters count against the score.

```
       [ Seed 0x5EED ]
              │
       ┌──────▼──────┐
       │ PRNG weight │
       │ Initialize  │
       └──────┬──────┘
              ▼
 ┌────────────────────────┐      probs      ┌────────────────────────┐
 │   Model Forward Pass   ├────────────────►│ Arithmetic Range Coder │
 └────────────┬───────────┘                 └───────────┬────────────┘
              ▲                                         │
              │ SGD Parameter Updates                   │ Actual Byte
              └─────────────────────────────────────────┘
```

### Protocol Contract & Updates
Both the Encoder and Decoder perform identical operations in absolute lockstep:
1.  **PRNG Init:** Regenerate identical embedding matrix $W_e$ (32-dim), LSTM gates weights $W_x$, $W_h$ (H=128), and output projection $W_o$ using seed `0x5EED`.
2.  **Probability Mapping:** Run forward pass `prev_byte -> LSTM cell -> Softmax` to get a 256-dimensional probability vector `probs`.
3.  **Cumcount Normalization:** Map float32 probabilities to integers summing exactly to $2^{14}$ (14-bit arithmetic coder precision) using stable sorting to resolve tied probabilities.
4.  **Bit I/O:** The encoder encodes the target byte; the decoder queries the range coder's interval and reads the byte.
5.  **Online Training:** Run backpropagation on the cross-entropy loss gradient ($d_{\text{logits}} = \text{probs} - \text{one\_hot}(y)$). Clip gradients to an L2 norm threshold of $5.0$, and run in-place SGD updates with learning rate $\eta = 0.05$.

## 3. `yellow_tucan_structural_range_v5` (Adaptive Parser-State Range Coder)

### Concept & Core Architecture
A dependency-free **context-mixing arithmetic coder** where probability tables are updated and mixed based on wikitext state variables.

```
                      ┌──────────────────────┐
                      │ Raw Input Character  │
                      └──────────┬───────────┘
                                 ▼
                      ┌──────────────────────┐
                      │ MediaWiki Parser     │──┐
                      └──────────────────────┘  │
                                                │ Active State Context
                                                ▼
 ┌──────────────────────┐   ┌──────────────────────┐   ┌──────────────────────┐
 │ Global Probability   │   │ Previous-Byte Prob   │   │ Structural Context   │
 │ Distribution (Order0)│   │ (Order-1 Context)    │   │ Prob (e.g., Template)│
 └──────────┬───────────┘   └──────────┬───────────┘   └──────────┬───────────┘
            │                          │                          │
            └──────────────────────────┼──────────────────────────┘
                                       ▼
                            ┌──────────────────────┐
                            │ PPM Escape / Backoff │
                            └──────────┬───────────┘
                                       ▼
                            ┌──────────────────────┐
                            │ Range Coder Interval │
                            └──────────────────────┘
```

### Table Selection and Mixing
Unlike neural context mixers, `yellow_tucan` uses PPM-style escape fallback modeling:
1.  **State-Directed Tables:** Individual probability tables are maintained for structural states (e.g., inside references `<ref>`, table regions `{|`, and brackets `[[`).
2.  **Backoff Logic:** If a character has never been seen in the current high-order structural state context, the coder outputs an `ESC` marker (PPM escape) and falls back to:
    $$\text{Structural State} \longrightarrow \text{Previous-Byte Order-1} \longrightarrow \text{Global Order-0}$$
3.  **Surplus/Deficit Alignment:** Softmax probabilities are scaled to cumulative frequency tables dynamically, checking for deficit/surplus offsets to ensure arithmetic intervals remain non-empty ($c_i \ge 1$).

## 4. `blue_dolphin_tree_macro_v1` (Parsed Template Tree Macros)

### Concept & Core Architecture
This is a **structural grammar-based pre-processor** that targets MediaWiki templates `{{name|arg1|arg2}}` specifically, bypassing the typical context-fragmentation bugs associated with byte-span macro mining.

```
                      ┌──────────────────────┐
                      │ Raw Input Wikitext   │
                      └──────────┬───────────┘
                                 ▼
                      ┌──────────────────────┐
                      │ Template Scanner     │ (Curly brace parser)
                      └──────────┬───────────┘
                                 ▼
                      ┌──────────────────────┐
                      │  Structural Hashing  │ (SHA-256 of template skeleton)
                      └──────────┬───────────┘
                                 ▼
                      ┌──────────────────────┐
                      │ Save admitted rule   │ (If frequency >= 3)
                      └──────────┬───────────┘
                                 ▼
                      ┌──────────────────────┐
                      │ Emit: Rule Ref ID +  │
                      │ Literal Arguments    │
                      └──────────────────────┘
```

### Pipeline
1.  **Scanning:** Parses all outer template boundaries (`{{ ... }}`).
2.  **Fingerprint Extraction:** Splits each template body into name and arguments. Generates a 64-bit structural fingerprint:
    $$\text{shape\_hash} = \text{SHA256}(\text{template\_name} \mathbin{\Vert} \text{sorted\_arg\_keys} \mathbin{\Vert} \text{arg\_count})[0:8]$$
3.  **Admittance Gating:** During encoding, templates are evaluated against a frequency tracker. If the shape appears $\ge 3$ times, it is registered.
4.  **Serialization:**
    *   **First occurrence:** Emits `OP_TEMPLATE_DEF`, registers the rule ID, serializes the template name and argument keys, then outputs the literal argument values.
    *   **Later occurrences:** Emits `OP_TEMPLATE_REF`, passes the rule ID, and lists only the raw argument lengths and literal argument values.
    *   **Other Text:** Emits `OP_LITERAL_RUN` for prose.
