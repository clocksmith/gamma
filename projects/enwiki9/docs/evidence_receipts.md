# enwiki9 Evidence Receipts

Every meaningful project fact should be backed by a receipt. This document
defines receipt shapes for gate results, memory-value rows, residual/SSE
shadow results, and official-score claims.

The result remains `positive_shadow_only` until it is implemented in the
compressor and passes same-scope roundtrip and determinism gates.

RSS failures can be recorded without a driver result when the guard kills the
candidate before an archive and roundtrip exist. Use:

```bash
python3 projects/enwiki9/tools/record_driver_result.py <candidate_id> \
  --guard-json <rss-guard-json-path> \
  --guard-only \
  --scope <scope-bytes> \
  --label <scope-bytes>_rss_guard_fail \
  --status active \
  --verdict "<exact RSS failure verdict>"
```

If `cmix21_gate_decider.py` reports
`bracket_lower_from_recorded_rss_failure`, the guard-only metadata row already
exists in `programs/<candidate_id>/meta.json`. Do not record the same RSS
failure again; use the printed lower-memory suggestion only after the heavy
lock is free.

For terminal gate receipts, prefer the decider's printed
`apply_terminal_command` over manually copying record commands:

```bash
<apply_terminal_command from cmix21_gate_decider.py>
```

The command is emitted only for terminal pass or RSS-failure receipts. It
includes `--launch-next` only for `promote_unchanged` and `--package-lower` only
for the RSS-bracketing path.

`cmix21_gate_decider.py --apply-terminal` fails closed when the current verdict
has no applicable terminal action. That protects the queue from silent no-op
handoffs on running, incomplete, roundtrip-failure, determinism-failure, or
guard-returncode-failure states.

`record_driver_result.py` records byte size, modified UTC, and SHA-256 for both
the driver result JSON and RSS guard JSON when those artifacts exist. These
fields bind a meta row to the exact receipts used for promotion or RSS
bracketing.

## Artifact Fingerprint Audit Receipt

Use this to verify that candidate `meta.json` rows still point at the exact
receipt files they claim. It is generated by:

```bash
python3 projects/enwiki9/tools/enwiki9_artifact_fingerprint_audit.py
```

```json
{
  "receipt_type": "artifact_fingerprint_audit",
  "project": "enwiki9",
  "artifact_checks": null,
  "status_counts": {
    "match": null,
    "missing_recorded_hash": null
  },
  "hash_mismatches": [],
  "missing_artifacts": [],
  "missing_recorded_hash_examples": [],
  "missing_recorded_hash_by_candidate": [],
  "duplicate_artifact_references": [],
  "ok": true,
  "rule": "Rows with recorded receipt hashes must match their artifact files."
}
```

`hash_mismatches` and `missing_artifacts` are hard failures. Rows counted as
`missing_recorded_hash` are legacy evidence: they can still be read, but future
terminal recordings should include fingerprint fields from
`record_driver_result.py`. The by-candidate repair queue makes the largest
legacy clusters visible, while duplicate artifact references show result files
that multiple labels point at.

Allowed verdicts:

```text
pass
running
rss_fail
roundtrip_fail
determinism_fail
receipt_incomplete
guard_returncode_fail
incomplete
```

`run_with_rss_guard.py` writes the guard JSON during the run with
`status: running`; the final receipt overwrites it with the completed return
code and guard verdict. A live guard without a driver result is not a
compression result, but it is valid evidence that a serialized gate owns the
lock and remains under observation.

`gate_evidence_status` makes that distinction explicit. A running RSS receipt
with no driver result must be `live_guard_monitor_only`; it cannot be treated as
a scored benchmark row or a promotion receipt.

For a running guard receipt, the compact status receipt includes both peak RSS
fields and latest-sample RSS fields. Peak fields decide boundary pressure;
latest-sample fields help identify the current process state while waiting for
terminal driver and guard receipts. It also records `rss_guard_json_bytes` and
`rss_guard_json_mtime_utc`, making stale guard receipts visible in the operator
handoff. `rss_guard_json_sha256` fingerprints that receipt file; it is an
artifact identity check, not an archive score.

When a cmix process is observed, `active_cmix_mode` must identify the native
phase. Expected values are `text_compress` for `-t`, `compress` for `-c`,
`decode` for `-d`, `no_preprocess_compress` for `-n`, `preprocess_only` for
`-s`, or `unknown` if the command line cannot be parsed. During decode,
`active_decode_progress` must be derived from the `.cmix.temp` staging output
and the active gate scope. These fields are operator evidence only; they do not
become benchmark evidence until the driver and RSS receipts are terminal.

The local kill guard is single-process. The receipt still records
`active_tree_rss_kib`, `active_tree_margin_kib`, and
`active_tree_rss_warning` so an operator can see process-tree pressure without
mistaking it for the enforced guard contract.

`active_candidate_recent_artifacts` is a shallow read of the active candidate's
result directory. It is a handoff aid for locating existing driver and RSS
receipts; rows in that list are not benchmark claims by themselves.

`active_rows` is the process-table evidence for the serialized scorer lane.
The Markdown receipt renders it as `Active Runner Process Table` so the lock
owner, guard process, Python driver, and native cmix process are visible without
opening the delayed status log.

`observed_gate_command` parses the active driver command and verifies that it
matches the certificate's active candidate, active scope, and determinism flag.
This catches stale lock owners before a terminal receipt can be recorded or a
candidate can be promoted.

For gates launched before the live-receipt guard code was active in the running
Python process, the final guard JSON may be absent until the command exits.
Use the generated operator status receipt for process-table RSS observation and
keep the gate verdict as `wait_for_gate_receipts`.

## Where Receipts Are Summarized

| Receipt type | Summary owner |
|---|---|
| `operator_status` | Generated `docs/status_receipt.md` and `docs/status_receipt.json`. |
| `gate_result` | `CMIX21_LOCK_SAFE_QUEUE.md` for cmix21, `ALGORITHMS.md` for algorithm status, `docs/evidence_matrix.md` for generated exact-result rankings. |
| `memory_value` | `CMIX21_LOCK_SAFE_QUEUE.md` and generated `docs/cmix21_memory_valves.md`. |
| `memory_surface_scan` | Generated `docs/cmix21_memory_surfaces.md`. |
| `shadow_residual` | `docs/residual_shadow_matrix.md`, `RESIDUAL_CERTIFICATE_REPORT.md`, `RESIDUAL_ROUTER_LOCK_SAFE_REPORT.md`, or `FX2_SC.md`. |
| `official_claim` | `UPPER_BOUND_CERTIFICATE.md` and `docs/official_accounting_checklist.md`. |
